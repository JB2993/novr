### Executive Summary
This diff reworks the VR UI cursor system from a camera-dependent screen-space pipeline to a world-space canvas-intersection approach. It introduces a new `VrCanvasHitTester` with explicit canvas registration and fallthrough logic, refactors `VrUiCursor` to use direct `GraphicRaycaster`/`ExecuteEvents` for event dispatch (replacing the VirtualMouse intermediate), wires canvas registration into all VR canvas-creating components, and adds extensive diagnostic logging. The architectural direction is sound, but the diff is a partial implementation (Phase 1 complete, Phase 2 deferred). Risk is **moderate**: no correctness bugs found, but there are design gaps, dead code, and per-frame allocations that degrade over time.

### Strategic Concerns

#### Architecture: Partial Phase Implementation
- **severity**: info | **confidence**: high
- **Area**: VrUiCursor, VrCanvasHitTester
- **Rationale**: The plan defined two phases: Phase 1 (world-space hit-test, done) and Phase 2 (panel-relative mapping, not done). The remaining angle intermediary at lines 434-435 of `VrUiCursor.cs` means the cursor-to-mouse mapping still uses a hardcoded angular sweep (±45° pitch, ±65° yaw) instead of mapping the companion window directly to the canvas rect. This is functional but means the cursor can "float" off the canvas edge or have mismatched horizontal/vertical sensitivity. The known anisotropic divergence (Term B from the bug brief) is mitigated but not eliminated — the cursor is now anchored to the canvas surface but the ANGLE that determines which surface point is hit still depends on the mouse position via a fixed FOV assumption.
- **Recommendation**: Implement Phase 2 panel-relative mapping as described in the plan (Task 4). The key change is replacing the angle-based direction with direct mapping of mouse normalized coordinates to canvas rect UV coordinates.

#### Performance: Per-Frame Allocations in Hot Path
- **severity**: warning | **confidence**: medium
- **Area**: VrCanvasHitTester, VrUiCursor
- **Rationale**: Three allocation sources in per-frame code paths: (1) `RaycastCanvases`/`RaycastCanvasPlanes` allocate a `List<(float,...)>` each call (up to 2x per frame in mouse path), (2) `HasGraphicAtPoint` in `RaycastCanvases` allocates `PointerEventData` per candidate, (3) `FirePointerEvents` allocates `List<RaycastResult>` per frame. On Quest/Android VR hardware, sustained GC collections cause visible frame drops. The existing codebase has a caching pattern for `_pointerEventData` (line 267) but the list allocations aren't cached.
- **Recommendation**: Use `ListPool<T>` from the Unity community, or cache static lists with `.Clear()`. `PointerEventData` should be cached per-canvas or globally reused.

#### Architecture: Event Dispatch vs Cursor Positioning Disconnect
- **severity**: info | **confidence**: medium
- **Area**: VrUiCursor
- **Rationale**: The cursor is positioned using world-space ray-canvas intersection (`RaycastCanvasPlanes`), but event dispatch (`FirePointerEvents`) still uses the screen-space round-trip (`GetScreenPoint()` → `GraphicRaycaster.ScreenPointToRay` via camera). This means the cursor position is decoupled from camera pose (good), but event targeting is NOT decoupled (the `GraphicRaycaster` shoots from the camera's current position through the screen point). When these two code paths use different camera poses (head moves between `Update()`'s cursor-position calculation and `LateUpdate()`'s... wait, LateUpdate is empty), event targeting can drift from the visible cursor.
- **Recommendation**: Either (a) move VirtualMouse feed to LateUpdate as originally planned to unify the projection/unprojection camera poses, or (b) eliminate the screen-space round-trip entirely by doing hit-testing in world-space with `GraphicRaycaster.Raycast()` using a correctly-positioned `PointerEventData`. Option (b) is more thorough but requires deeper changes to how `GraphicRaycaster` works.

### Positive Observations
1. **Clean registration API**: `VrCanvasHitTester.Register/Unregister` is well-designed. Using Unity lifecycle (OnEnable/OnDisable, Awake/OnDestroy) for registration is idiomatic and prevents stale references.
2. **Removed VirtualMouse complexity**: The old code had `RestrictUIModuleToVirtualMouse` with InputAction binding overrides that was fragile and hard to debug. Replacing it with direct `GraphicRaycaster` + `ExecuteEvents` is architecturally simpler and eliminates the synthetic device dependency.
3. **CameraMatches handles nested canvases**: Line 198-209 correctly handles the edge case where nested canvases have `worldCamera = null` by falling back to the root canvas's camera. This is a common Unity pitfall.
4. **Diagnostic quality**: `LogRaycastAtCursor` is comprehensive — it captures per-frame camera pose snapshots, screen point comparisons, GraphicRaycaster results, forward orientation checks, and lossy scale warnings. This level of instrumentation will make future debugging much easier.
5. **Canvas forward orientation check**: Lines 785-786 and 797-798 in the diagnostics correctly identify flipped canvases (positive orientDot) and negative lossyScale, which are common Unity VR pitfalls that are very hard to spot without tooling.
6. **Offscreen guard**: The `_isOffscreen` flag in `GetScreenPoint()` (line 119) prevents phantom clicks when the cursor is behind the camera. A well-implemented defense against a class of hard-to-debug VR bugs (mirrored coordinates sending clicks to opposite side of the screen).
